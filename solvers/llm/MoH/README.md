# MoH on ATSP

**Meta-Optimization of Heuristics** — Shi et al., *Generalizable Heuristic
Generation Through LLMs with Meta-Optimization*, ICLR 2026
([paper](https://arxiv.org/abs/2505.20881) ·
[upstream code](https://github.com/yiding-s/MoH)) — retargeted from symmetric
TSP to the **Asymmetric** Travelling Salesman Problem.

Every command lives in [`scripts/llm/MoH/RUNBOOK.md`](../../../scripts/llm/MoH/RUNBOOK.md).
The short version:

```bash
pip install -r envs/llm/MoH/requirements.txt
cp envs/.env.example envs/.env && $EDITOR envs/.env     # OPENAI_API_KEY=sk-...

python python_scripts/llm/MoH/prepare_data.py --config synthetic
bash scripts/llm/MoH/smoke.sh                          # free, no LLM calls
bash scripts/llm/MoH/baselines.sh                      # free; also sets your thresholds
python python_scripts/llm/MoH/run_moh_atsp.py --task atsp_gls
bash scripts/llm/MoH/benchmark.sh
```

## 1. What MoH does, and why it is the odd one out

Every other LLM heuristic-design framework in this repository searches over
**heuristics** with a fixed evolutionary operator: EoH has five prompt
strategies, ReEvo has reflection, HSEvo has diversity control, MCTS-AHD has a
tree. MoH searches over the **operator itself**.

It runs two nested loops:

**Outer loop — optimizer design.** The current meta-optimizer `I*_{t-1}` is
invoked on a population of *heuristic-optimizers* and writes M candidates. A
candidate is a Python function `improve_algorithm(population, utility,
language_model, function_format, task)` — an entire optimization strategy,
generated by the LLM. Because heuristic-optimizers and meta-optimizers share one
signature (Figure 3 of the paper), the meta-optimizer can be applied to itself;
that self-invocation is what the abstract means by "(self-)invocation" and is
why both populations are the same class.

**Inner loop — heuristic design.** Each candidate optimizer is run once per
downstream subtask, where it evolves that subtask's heuristic population and
returns the best heuristic it found. The candidate's score is the size-weighted
mean of those, Eq. (2): `U(I) = Σ w_i · U_i(h_i, D_i)` with `w_i = s_i / Σ s_j`.
The best-scoring candidate becomes `I*_t`.

The subtasks are **instance sizes** — TSP20/50/100/200 in the paper, ATSP 50/200
here. That is the whole generalisation argument (Figure 1): heuristics evolved on
one size degrade sharply on others, and MoH's answer is to evolve the optimizer
across sizes at once, then reuse it.

So a MoH run produces two kinds of artefact, and it is worth being clear about
which is the result:

| artefact | what it is |
|---|---|
| `best_meta_optimizer.py` | `I*_T` — the discovered optimization strategy. The thing the method is about, and the thing that transfers. |
| `best_heuristic_<task>-<size>.py` | one heuristic per subtask size. |
| `best_heuristic.py` | a copy of the largest subtask's winner, so the shared benchmark scripts find it where they find every other framework's. |

`I*_T` can be fed straight back in to design heuristics for a size or a task it
was never trained on — the paper's *inference stage*, and much cheaper than
training:

```bash
python python_scripts/llm/MoH/run_moh_atsp.py --task atsp_gls \
    --inference runs/llm/MoH/atsp_gls-gls/<date>_<time>/best_meta_optimizer.py \
    --data multisize --sizes 400
```

## 2. What changed from upstream, and why

The framework is upstream's. Algorithm 1, the two populations, the individual
format, the optimizer signature, the loop-depth audit, the size-weighted utility
and the prompt architecture are all unchanged. What changed is the problem, the
plumbing around it, and six bugs.

### 2.1 The problem

| | upstream MoH | here |
|---|---|---|
| problem | symmetric TSP (+ BPP, CVRP) | ATSP, `d[i][j] ≠ d[j][i]` |
| tasks | `tsp_gls` | `atsp_gls`, `atsp_kgls`, `atsp_constructive` |
| subtasks | TSP sizes 100, 200 | ATSP sizes 50, 200 (configurable) |
| instances | pickled TSP coordinate sets from a Drive link | generated ATSP matrices + the 19 TSPLIB ATSP instances |
| local search | 2-opt + relocate, numba-JIT, float32 signatures | Or-opt + swap, plain NumPy, shared with every other solver here |
| model | `gpt-4o` in the shipped config | `gpt-4o-mini`, which is what the paper actually reports and what this benchmark standardises on |

**Why 2-opt is gone.** 2-opt reverses a tour segment. Under an asymmetric matrix
every arc inside the reversed segment flips direction, so the move is neither
O(1) to evaluate nor cost-preserving — it is simply not the same move. The
engines here use the Or-opt + swap search in `atsp/engines`, shared with EoH,
ReEvo, HSEvo and MCTS-AHD so that a gap difference between frameworks is a
difference between their searches.

**Why numba is gone.** It only bought speed on the 2-opt kernels that no longer
exist, and it cost a compiler dependency. The budget is calibrated instead:
`atsp_utils.train_iter_limit` converts the benchmark's wall-clock budget into an
iteration count for *this* machine, so a score never depends on machine load
while still spending what the benchmark spends. Re-measure with
`bash scripts/llm/MoH/calibrate.sh`.

**Where the ACO task went.** Nowhere — it was never added. MoH's inner loop
evaluates a candidate once per subtask per iteration, and a stochastic 20-ant
colony makes that utility noisy enough that the outer loop would be selecting
optimizers on sampling noise rather than on quality. The MCTS-AHD and ReEvo
sides carry the ACO task; add it here only with a fixed seed and a much larger
instance count.

### 2.2 The design space, versus the other frameworks

This is the one place where MoH's tasks are *not* interchangeable with the
others', and it is upstream's choice rather than ours:

* **ReEvo / HSEvo / MCTS-AHD `atsp_gls`** — the LLM writes `heuristics(distance_matrix)`,
  a **static** guide matrix computed once per instance.
* **MoH `atsp_gls`** — the LLM writes
  `update_edge_distance(edge_distance, local_opt_tour, edge_n_used)`, called at
  **every perturbation step**, with the current local optimum and the penalty
  history in hand. Strictly the larger space, and the one all of the paper's
  improvement-heuristic results live in.

Everything downstream of that — the instances, the local search, the
per-instance budget, the objective — is identical. A heuristic from one
framework cannot be dropped into the other's engine, but the numbers they report
mean the same thing.

### 2.3 Where the settings live

Upstream keeps data paths and engine budgets as constants inside `eval.py`,
which is understandable — `eval.py` runs as a subprocess with no Hydra context.
Here they are configuration, read from plain YAML by `atsp_utils.load_config`:

```
configs/llm/MoH/cfg/
├── config.yaml            iterations, populations, budgets, mode
├── problem/<task>.yaml    subtask sizes, seed thresholds, timeout, description
├── data/<name>.yaml       which instances the search and the report use
├── evaluation/<task>.yaml engine budgets, identical to the MCTS-AHD side's
├── llm_client/*.yaml      openai (gpt-4o-mini) / litellm / local / stub
└── hydra/output/local.yaml  runs land in runs/llm/MoH/
```

`moh.py` forwards the choices to every evaluation subprocess as `ATSP_DATA` and
`ATSP_EVAL_BUDGET`. Nothing is hardcoded in a task file.

### 2.4 Bugs fixed

Each of these cost a *run* rather than a result, which is why they are worth
listing:

1. **Unbounded seeding.** `generate_seed_algorithm` looped `while cur_pop_size <
   5` with no bound. If nothing cleared the acceptance threshold — what happens
   the first time you point it at a new problem and guess the threshold — it
   called the API forever. Now bounded by `cfg.seed_rounds`, relaxes the
   threshold by `cfg.seed_relax` between rounds, warns, and finally falls back to
   the task's committed seed function.
2. **A perfect score counted as a failure.** `try_improvement` tested
   `if not new_utility`, so a meta-utility of exactly `0.0` was discarded as an
   error. On ATSP a gap of 0.000% at n=50 is routine. Now checks `None`/`NaN`.
3. **Ideas and code drifted apart.** `try_improvement` stored the *old* optimizer
   source under the *new* idea, so the population's descriptions stopped
   describing its code. It stores the pair it actually scored.
4. **`"Error"` matched against the heuristic's own source.** The evaluation log
   begins with the candidate's code, and the parent scanned the whole file for
   the substrings `Traceback` and `Error` — so a heuristic with the word `error`
   in a comment was thrown away no matter how well it scored. Only the
   subprocess's own output is scanned now (`utils.utils.extract_eval_output`).
5. **`"random"` matched identifiers.** The determinism guard rejected any source
   containing the substring `random`, including `randomised_weight`. It now
   matches actual uses of the random modules.
6. **Budget checked only between iterations.** Seeding could overshoot
   `max_eval_calls` by hundreds of calls. It is checked at every evaluation.

Two smaller ones: `prompt_batch` opened one thread per message (a generated
optimizer with a 40-message batch would open 40 sockets and be rate-limited into
the retry path), and `seed_algorithm_improved` sorted its candidates
`reverse=True` before taking the head, so each round kept the *worst* ones.

### 2.5 What was removed

Upstream's `problems/tsp_gls/` and `prompts/tsp_gls/` (symmetric TSP), the
vendored `cfg/` tree (now `configs/llm/MoH/cfg/`), `uv.lock`, `pyproject.toml`,
`assets/`, the solver-local `.gitignore` and an empty `utils/pop.json`.

They are **moved, not deleted**:

```bash
bash scripts/llm/MoH/prune_upstream.sh --dry-run   # see what would move
bash scripts/llm/MoH/prune_upstream.sh             # move it
rm -rf solvers/llm/MoH/_to_delete                  # when you are happy
```

`_to_delete/` is git-ignored, so the moved files leave `git status` immediately
and stay on disk until you say otherwise. The script writes a README in there
recording what each item was replaced by.

One upstream file was kept and moved: the discovered optimizer from the paper's
TSP runs is now `problems/meta/paper_optimizer.py`. It is not a result here —
it was found on symmetric TSP — but it is a stronger `I_0` than the plain seed
and a worked example of what a discovered optimizer looks like.

### 2.6 Exact Benchmark Evaluation & CPU Load Management

Guided Local Search (GLS) on ATSP is a CPU-bound NumPy optimization loop with a wall-clock time limit (e.g. `time_limit: 30.0s` per instance).

> [!IMPORTANT]
> **Check CPU Load Before Running Official Benchmark Evaluations**:
> If heavy background processes (such as data generation, parallel compiling, or another training run) are active, CPU cores become saturated. Under heavy contention, Python executes fewer local search iterations within the 30.0s time limit, artificially increasing the optimality gap.

#### How to Check for Processes Saturating CPU Cores:

1. **Check Top CPU-Consuming Processes**:
   ```bash
   ps aux -r | head -n 10
   ```
2. **Check Running Python / Pytest Processes**:
   ```bash
   ps aux | grep -E "python|pytest" | grep -v grep
   ```
3. **Live Interactive CPU Monitor**:
   ```bash
   top -o cpu
   ```
4. **Kill Stuck / Runaway Background Processes**:
   ```bash
   kill -9 <PID>
   # or terminate all background python jobs:
   pkill -9 -f python
   ```

├── problems/
│   ├── meta/                  I_0, the first-step optimizer, the paper's optimizer
│   ├── atsp_gls/              eval.py + gls.py + gpt.py (the live candidate)
│   ├── atsp_kgls/             eval.py + kgls.py + gpt.py
│   └── atsp_constructive/     eval.py + gpt.py
├── prompts/
│   ├── meta/desc.txt          the optimizer-generation prompt (Appendix D.1)
│   ├── helper/check_iter.txt  the loop-depth audit
│   └── <task>/                desc / task / plan / size / seed_func
└── utils/
    ├── population.py          heap-ranked populations (Section 3.3)
    ├── run_logger.py          everything a run writes

`problems/<task>/gpt.py` is scratch: `moh.py` overwrites it on every evaluation.
What is committed there is the task's seed rule, so `python problems/<task>/eval.py`
works standalone.

## 4. Configuration, in the order you will touch it

| key | default | what it controls |
|---|---|---|
| `problem` | `atsp_gls` | which downstream task |
| `problem.problem_size` | `[50, 200]` | **the subtasks.** One per size, weighted by size in Eq. (2) |
| `data` | `synthetic` | which instances the search and the report use |
| `n_iterations` | `15` | outer-loop iterations `T` |
| `pop_size` | `15` | both populations |
| `max_eval_calls` | `300` | heuristic evaluations **per subtask**; total = this × N |
| `problem.threshold` | per size | seed-acceptance bar; set it from `baselines.sh` |
| `mode` | `train` | `inference` reuses a trained optimizer, skipping the outer loop |
| `heu.model` / `meta.model` | `gpt-4o-mini` | inner- and outer-loop models, separately |

```bash
cd solvers/llm/MoH

python main.py problem=atsp_kgls
python main.py problem=atsp_gls problem.problem_size='[50,100,200,400]' data=multisize
python main.py problem=atsp_gls n_iterations=20 max_eval_calls=200
python main.py problem=atsp_gls meta.model=gpt-4o          # stronger outer loop only
python main.py problem=atsp_gls llm_client@heu=stub llm_client@meta=stub  # free
```

**On `max_eval_calls`.** Upstream defaults to 1000 per task, which is the paper's
figure for TSP where an evaluation is a few seconds of numba-compiled search over
8 instances. Here an evaluation is ~10 s of pure-NumPy guided local search per
instance, so 1000 per subtask is roughly two days. The default of 60 gives 120
total on the two-subtask default — the same order as the 100 evaluations the
ReEvo and MCTS-AHD sides use, so the frameworks are compared at comparable cost.
A claim about search efficiency only means something when the budget is fixed.

**On `problem.threshold`.** MoH admits a sampled seed heuristic into a subtask's
population only if its utility is below this. Set it too tight and the seeding
phase finds nothing, relaxes itself, warns, and eventually falls back — all of it
paid for in tokens. Run `bash scripts/llm/MoH/baselines.sh` first and set it a
little above the seed rule's own gap.

## 5. Logging: every run writes one directory

```
runs/llm/MoH/atsp_gls-gls/2026-08-18_09-30-00/
├── run.log                       everything logged and printed
├── llm_calls.jsonl               every prompt/response, tagged meta (outer) or heu (inner)
├── meta.json                     config snapshot, git commit, platform, argv
├── progress.jsonl                one line per outer iteration, written live
├── logs/meta_utility.csv         U(I) per iteration + whether it was accepted
├── logs/utility.csv              U_i(h) per subtask per iteration
├── pop/improver/, pop/subtask/   both populations after every iteration
├── code/improver/candidate_*.py  every optimizer proposed, accepted or not
├── evaluations/                  stdout of every evaluation + index.jsonl
├── best_meta_optimizer.py        I*_T
├── best_heuristic_<subtask>.py   one per subtask size
├── best_heuristic.py             the largest subtask's winner
└── summary.json                  utilities, LLM statistics, wall time
```

Three files answer most questions:

* **`progress.jsonl`** — did the meta-utility go down, and was any candidate
  accepted? A run where nothing is ever accepted is a run where the outer loop is
  not working, and that is nearly always a threshold or a budget problem.
* **`code/improver/candidate_*.py`** — what did the outer loop actually try? The
  rejected candidates are the evidence for whether it explored. Appendix E of the
  paper is a gallery of these: ACO-like, PSO-like, simulated annealing, tabu
  search, hybrids.
* **`evaluations/index.jsonl`** — how many evaluations failed, timed out or were
  unparsable? A high failure rate means the task prompt is not constraining the
  model enough, and it shows up here long before it shows up in the gap.

Keys never reach disk: the config snapshot in `meta.json` stores
`<redacted:N chars>`, and only *which* `.env` file was used is recorded.

## 6. Reproducing the paper's studies

| paper | how |
|---|---|
| Multi-task training (Fig. 1) | `--data multisize --sizes 50 100 200 400` |
| Inference on unseen sizes (§3.2) | `--inference <best_meta_optimizer.py> --sizes 400` |
| Population size (Table 5) | `--set pop_size=1` / `5` / `10` |
| Different LLMs (Table 4) | `llm_client@heu=litellm heu.model=<provider>/<model>` |
| Cost accounting (Tables 10–12) | `summary.json`: `llm_calls`, `approx_prompt_tokens`, `eval_calls`, `minutes` |
| The generated optimizers (Appendix E) | `code/improver/` in any finished run |

Not reproduced, and deliberately: the paper's cross-problem experiments (BPP,
CVRP, QAP, Acrobot). This repository is an ATSP benchmark.

## 7. Tests

```bash
python -m pytest tests/llm/MoH/ -v
python -m pytest tests/llm/MoH/ -v -m "not slow"     # skip the real-engine runs
```

No test makes an LLM call — the stub client answers all four kinds of prompt MoH
sends offline. The suite checks the configs, the data splits, the size filtering
(including that a missing size *raises* rather than silently falling back), the
prompts, the seed functions, the evaluation contract, the population semantics,
and a full offline run end to end.
